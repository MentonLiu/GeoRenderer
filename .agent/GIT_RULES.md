# Git 工作流规则

## 长期分支

- `main` 是稳定分支，负责版本号更新和正式发布。发布时将已确认的 `dev` 合并到 `main`，在 `main` 更新版本号、更新 `CHANGELOG.md`，并创建对应版本标签。
- `dev` 是日常开发集成分支，从 `main` 建立。功能开发、缺陷修复和重构都先进入 `dev`，不要直接提交到 `main`。
- `docs` 从 `main` 建立，专门承载文档更新和文档提交。文档整理完成后将 `docs` 合并回 `main`。

## 开发分支

- 每项功能、修复或重构从 `dev` 最新提交建立独立分支，建议使用 `feat/<简述>`、`fix/<简述>`、`refactor/<简述>` 等名称。
- 开发完成后将该分支合并回 `dev`。合并前先同步 `dev` 的最新提交，并解决冲突；合并后删除已完成的短期分支。
- 版本发布完成后，将 `main` 的更新同步回 `dev`，使后续开发基于最新版本。

## 提交约定

- 提交说明使用简洁的动作描述，并采用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:` 等类型前缀。
- 版本发布提交使用 `chore: release <版本号>`，并只包含发布所需的版本、变更记录和元数据更新。
- 不把无关的功能、修复和文档改动混在同一个提交中；不要改写已共享的提交历史。

## 分支流向

```text
main ──► dev ──► feat/*、fix/*、refactor/* ──合并回──► dev ──发布──► main
  └────► docs ────────────────────────────────────────合并回──► main
```
